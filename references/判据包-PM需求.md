# 判据包：PM / 需求文档（场景 prd）

> 裁判和静态脚本共用这份判据。裁判判开放项时照逐条判据说「通过/不通过 + 理由」，
> 不许写「回答要好」这类空话——空话判据等于没有判据。

## 一、静态项（脚本已判，这里只记口径）

| 指标 | 判法 | 达标线（建议值，人拍板） |
|---|---|---|
| 可验收率 | 条目含「怎么算对」痕迹的比例 | ≥ 70% |
| 模糊词密度 | 每千字模糊词个数 | ≤ 3 |
| 未定死显式化 | 「待定/视情况」全在明面上挂牌 | 隐式留白 = 0 |

## 二、裁判项（成对对冲，两维分开打分）

### 具体性 × 可实现性

**具体性——这条把细节定死了吗？通过长这样：**
- 有数值、字段、格式、状态、边界（「超 5 秒返回超时错误码 E1021」）；
- 行为可观察：输入什么 → 做什么 → 出什么，一眼能转成验收用例。

**不通过长这样：**
- 「需要良好的体验」「合理处理异常」「支持常用格式」——全是没定死的表述；
- 只有方向和原则，没有落到可核对的条款。

**可实现性（对冲，防往死里写）——是不是画大饼/写过头？不通过长这样：**
- 要求当前技术条件做不到的（「实时精确预测用户明天要什么」）；
- 把实现方式写死到不该管的层（规定用哪个算法、哪个库，锁死实现自由度）。

### 边界完备度 × 冗余度

**边界完备度——通过长这样：**
- 每条主流程配了异常/失败/超时/空值的处理：谁兜底、降级成什么、报给谁。

**不通过长这样：**
- 只写顺利路径；出错怎么办只字未提，或一句「做好异常处理」带过。

**冗余度（对冲，防刷覆盖）——不通过长这样：**
- 同一个意思拆成五条凑数；
- 车轱辘话换着说，条目数涨了信息没涨。

## 三、过度约束率（对冲项，计数）

把实现细节当需求写的条目：指定算法、库、内部结构，而这些并非业务约束。
占比高说明 PRD 越权成了技术方案——需求要定死「做什么、怎么算对」，不是「怎么实现」。

## 四、未定死清单的归口

以下都进未定死清单，每条注明缺什么：
- 静态扫出的「待定/TBD/视情况」；
- 裁判判「不通过」但说不清该写什么的条目（= 判据缺口）；
- 重档多跑时 N 遍说法不一致的决策点。

清单条目格式与确认点选项卡见 templates/。
