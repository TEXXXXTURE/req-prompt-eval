# 缺陷归因与回流（「不满意」怎么变成数据）

评出来的分不满意时，**不量化满意度**，强迫归因。归因只有三个去向：

## 三去向

| 去向 | 什么时候 | 动作 |
|---|---|---|
| ① 违了已有判据 | 判据有、产出没做到 | 记一次 fail，进评分卡；查产出为什么不达标 |
| ② 判据缺口 | 没违任何判据，但就是不对 | 这是需求/提词的留白——补判据或进未定死清单 |
| ③ 判据本身错了 | 判据要求得不合理 | 改判据包，注明改因 |

**归因不出去的「不满意」对流程没有信息量**——说不出哪里不对，下游也修不了。
归因不出来的默认走 ②：先记进未定死清单，攒着，定期回看是否该升判据。

## 回流规则（重档产出怎么用）

- 多跑对比中 N 遍不一致的决策点 → 未定死清单（这是留白的直接证据）；
- 真实使用中下游追问/猜错的点 → 同样进未定死清单；
- 未定死清单每攒够一批，人工过一遍：定死的补进需求/提词，不值得定死的显式标「留白，接受」。

## 与分数台账的关系

台账（JSONL）每次跑追加一行：时间/对象/档位/分项/总分/备注。
对比改动效果 = 横着看同一对象的多行：改了什么（备注）→ 分项怎么变。
备注必写「本次改动了什么」，不然分变化无法归因。

## 红线

- 评测不提供改写建议——报告说哪里不行，不说「应该写成什么样」；
- 不给「满意度」打分——只有违例数、达标率、一致率可计数。
